# Durability (roadmap Step 4, moved ahead of Steps 2-3)

## Goal

An agent run is a Temporal workflow. It survives worker crashes and restarts,
resumes without repeating completed model or tool calls, and outlives the HTTP
request that started it. `temporalkernel` passes the same conformance suite as
`memkernel`, plus a kill-the-worker chaos test.

Why now, before tools (Step 2) and streaming (Step 3): approvals (`Await`) and
streaming both need runs that exist independently of a request. Building that
on an in-process run manager first would be thrown away when Temporal lands.

## Verified facts (Temporal Go SDK v1.51.0, read from source)

- **Local activities are not a fit for steps.** Anonymous functions as local
  activities are deprecated ("their name is generated by the Go runtime and is
  not deterministic"), and local activities must finish well inside the
  workflow task timeout (default 10s). Model calls take 30-120s.
- **Regular activities are registered by name** (`RegisterActivityWithOptions`)
  and take serializable input. A closure capturing its input can't be sent.
- **`workflow.Context` is not a `context.Context`**: its `Done()` returns a
  Temporal `Channel`.
- **Replay is available**: `worker.NewWorkflowReplayer()` with
  `ReplayWorkflowExecution` / `ReplayWorkflowHistory`.
- **Hermetic dev server for tests**: `testsuite.StartDevServer` (downloads and
  caches the Temporal CLI binary).
- Compose already runs Temporal 1.24.2 (`localhost:7233`, UI on `:8088`).

## Key decisions

1. **Steps become named activities with explicit input.** Replace the closure
   form `Step(name, fn)` with registered activities:

   ```go
   // kernel
   type Activity[In, Out any] struct {
       Name string
       Fn   func(context.Context, In) (Out, error)
   }
   func Call[In, Out any](c Ctx, step string, a Activity[In, Out], in In) (Out, error)
   ```

   `Ctx` gets `Call(step, activity string, input []byte) ([]byte, error)`;
   `kernel.Call` is the typed wrapper (replaces `StepT`). One mechanism for all
   kernels: memkernel looks the activity up in its own registry and journals
   it; temporalkernel calls `workflow.ExecuteActivity` by name. Activities are
   registered on the kernel/worker at startup, so dependencies (model client,
   tools) are bound there, not captured per call.

2. **`kernel.Ctx` stops embedding `context.Context`.** Workflow code must not
   use Go context semantics on Temporal anyway. Activity bodies still receive a
   real `context.Context`. Cancellation surfaces as an error from `Call`
   (memkernel: the run's context ended; Temporal: workflow cancelled), so the
   executor's `fatal` check uses the error, not `c.Err()`.

3. **Delete `internal/stepreg`.** It was a global registry to dispatch closures
   by name; per-kernel activity registration replaces it with no global state.

4. **One worker binary, `cmd/worker`.** Registers the agent workflow and its
   activities on one task queue (`agent`). Replace the `worker-workflow` /
   `worker-activity` stubs. Separate queues for I/O vs CPU work come later, when
   there is CPU work.

5. **Retries: the client handles HTTP, Temporal handles worker death.** The
   model client keeps its own backoff for 429/5xx. Activity retry policy:
   `MaximumAttempts: 3`, short `StartToCloseTimeout` per activity kind (model:
   3m, tool: per tool). Non-transient errors (4xx, bad input) are returned as
   non-retryable application errors so Temporal doesn't retry them.

6. **`/api/chat` starts a workflow and waits for its result.** Workflow ID =
   run ID. Same request/response UX as today, but if the browser disconnects or
   the server restarts, the run still finishes on the worker. Temporal is
   required in dev (`make up` already starts it); no memkernel fallback in the
   server.

7. **Continue-As-New is deferred.** A run is one turn capped at 8 model calls,
   so history stays small. Revisit when a run spans a whole session; the
   `kernel.ContinueAsNewer` seam stays.

## Testing

- **Conformance against temporalkernel**, using `testsuite.StartDevServer`.
  Harness mapping:
  - `Register` / `RegisterActivity` → worker registration.
  - `Run(runID, ...)` on a new ID → `ExecuteWorkflow` + `Get`. On an ID that
    already completed → replay its history against the current registrations
    with `WorkflowReplayer` and return the recorded result. That is what
    "re-running replays" means on Temporal, and it is how the nondeterminism
    test detects changed code.
  - `Signal` to a run that hasn't started → buffered in the harness and sent
    with `SignalWithStartWorkflow` when `Run` starts it.
- **Crash test reworked around `Harness.Restart()`.** Today's
  `CrashMidStepResumes` cancels the run's context, which on Temporal only stops
  the client waiting. Instead the harness exposes `Restart()`: memkernel
  cancels the in-flight run and reruns it; temporalkernel stops the worker and
  starts a new one. The test asserts the step that finished before the
  restart runs exactly once.
- **Chaos test (executor on Temporal):** a fake model whose turn-0 reply calls
  a tool; the tool activity blocks until the test stops worker A; worker B
  picks the run up. Assert the run completes and model turn 0 was called once.
- **Mutation check:** the conformance suite must fail against temporalkernel
  with replay deliberately broken (e.g. `Call` running the activity body
  locally), as it does for memkernel.
- Existing memkernel, executor and reducer tests keep passing after the
  `Call` refactor (executor tests register the fake model/tools as activities).

## Delivery steps

Each step ends with `make test` green.

1. **Contract refactor on memkernel.** `kernel.Activity`/`Call`, drop
   closure `Step` and the `context.Context` embed, delete `stepreg`, update
   memkernel, conformance (activities + `Restart`), executor (activities,
   Runner split), `/api/chat`. Behaviour unchanged.
2. **temporalkernel + conformance.** Implement the adapter and the Temporal
   harness on `StartDevServer`; all 8 conformance tests pass; mutation check.
3. **Worker + server wiring.** `cmd/worker`, Temporal client in `cmd/server`,
   `/api/chat` via `ExecuteWorkflow`, `make dev` runs the worker. Manual check:
   chat works; kill the worker mid-reply, restart it, the reply still arrives.
4. **Chaos test** in CI form (dev server, two workers, fake model).
5. **Docs**: update `AGENTS.md` (durability rules, request flow, repo map,
   status) and mark Step 4 done in the roadmap.

## Risks

- **Contract churn.** Changing `kernel.Ctx` touches every kernel, the
  conformance suite and the executor. Doing it first, on memkernel alone, keeps
  it reviewable and keeps behaviour fixed while the shape changes.
- **Replay-based harness differs from a real crash.** Covered by the separate
  `Restart` and chaos tests, which use real worker loss.
- **Dev server download in tests.** `StartDevServer` needs network on first
  run; cached afterwards. Skip with a clear message when it can't start.
- **Payload size.** Activity inputs/outputs go into Temporal history (default
  limit ~2MB per payload). Tool output is already capped by
  `Limits.MaxToolOutput`; the conversation history grows per turn. Fine for one
  turn, revisit with Continue-As-New.
- **Version skew.** SDK v1.51.0 against server 1.24.2 in compose; verify on
  step 2 and bump the compose image if needed.
